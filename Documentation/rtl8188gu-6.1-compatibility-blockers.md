# RTL8188GU / RTL8710BU Backport — Linux 6.1 Compatibility Blockers

Target branch: `rtl8188gu-backport-6.1-nh`  
Target base: GKID-NH commit `f391d5a36ae325a4f3abdf497335abae87734a05`  
Target kernel: Linux 6.1.177-GKID-r663  
Upstream reference: `torvalds/linux` commit `70664495e3d24803ec47ccaccee9a822220558a0`

## Status

This is an audit document only. No kernel driver source, Kconfig, Makefile, defconfig, firmware, or existing driver code has been changed by this audit. No build or runtime test has been performed.

## Finding

The upstream RTL8710BU/RTL8188GU support is not a self-contained new subdriver. The target 6.1 rtl8xxxu implementation predates several interfaces and core mechanisms used by the upstream driver. Copying only `rtl8xxxu_8710b.c`, adding its object to the Makefile, or adding USB ID `0bda:b711` would be incomplete and unsafe.

The upstream change modifies 12 files in the rtl8xxxu directory and introduces a new 1,879-line subdriver. Its shared-core changes are essential to operation.

## Confirmed target/upstream API differences

### 1. File-operations interface

The target 6.1 `struct rtl8xxxu_fileops` lacks several callbacks present in the upstream interface, including:

- chip identification
- chip-specific efuse read
- PHY-statistics parsing
- LC calibration
- burst initialization
- RSSI reporting
- crystal-cap setting
- chip-specific CCK RSSI conversion

The target core also calls some operations directly rather than dispatching through the newer callbacks. A safe port must introduce these interfaces with compatibility defaults and update every existing initializer/call site consistently. Do not change a callback signature in isolation.

### 2. Register access and RTL8710B register window

RTL8710B does not use the normal 0x0000–0x00ff register window in the same way as the older chips. Upstream adds RTL8710B-specific address remapping in all 8-, 16-, and 32-bit USB register read/write helpers. It also adds indirect system-register access protected by a dedicated mutex.

The target core has neither the address remapping nor the indirect-access synchronization. This must be implemented as chip-gated behavior so existing chips retain their original register addresses and locking behavior.

### 3. Firmware download path

Upstream adds RTL8710B-specific firmware control-register handling, including the alternate firmware-download control register and special setup before firmware transfer. The generic target 6.1 download path assumes the older register layout.

The new subdriver declares two firmware variants:
- `rtlwifi/rtl8710bufw_SMIC.bin`
- `rtlwifi/rtl8710bufw_UMC.bin`

The correct variant must be selected from chip/package identification. Do not guess a firmware variant or silently package an unverified file.

### 4. Efuse and chip identification

The upstream subdriver has a dedicated chip-identification and efuse-reading/parsing path, including an RTL8710BU-specific efuse layout. The target core currently uses its older generic efuse flow. The port must ensure the new path is selected only for RTL8710B while all existing chips keep their current path.

### 5. PHY statistics and receive parsing

RTL8710B uses the Jaguar2 PHY-stat formats (types 0, 1, and 2). Upstream adds the structures and parser, then dispatches PHY-stat parsing through the chip file-operations table. The target core has an older fixed parser and does not expose that dispatch point.

This requires coordinated header and RX-core changes, not merely adding the new parser source file.

### 6. Other core integration points

The upstream core also includes RTL8710B-specific handling for:
- TX descriptor checksum quirk
- initialization and power sequencing
- firmware start/reset
- burst and aggregation setup
- interrupt and RX filter configuration
- USB probe ID-to-fileops mapping
- initialization and destruction of the indirect-register mutex

These changes must be reviewed individually against the target 6.1 code. Avoid wholesale replacement of the target core with a newer upstream file.

## Existing-driver regression protection

The upstream commit also changes several existing subdriver files because shared interfaces evolve. For this backport:

1. Preserve all existing target 6.1 driver source and behavior.
2. Add new RTL8710B behavior behind explicit `priv->rtl_chip == RTL8710B` or equivalent chip-specific dispatch.
3. If shared interfaces must change, update all existing implementations and initializers in the same reviewed change.
4. Compare the complete diff against the target baseline after each logical patch.
5. Build with the existing GKID configuration and verify that the existing Realtek modules still compile.
6. Do not enable `CONFIG_RTL8XXXU` in the user's build configuration until the driver source is complete and build-verified.

## Recommended port sequence

1. Inventory target and upstream shared structures, helper APIs, and all existing file-operations initializers.
2. Design backward-compatible file-operations extensions, retaining old behavior for existing chips.
3. Port RTL8710B register remapping and indirect access with chip-gated behavior.
4. Port firmware and efuse dispatch, including package identification and firmware declarations.
5. Port Jaguar2 PHY-stat structures and receive-parser dispatch.
6. Port the new RTL8710B subdriver and only the exact register definitions it needs.
7. Port the remaining chip-specific core initialization, power, TX, and USB-probe changes.
8. Review all existing Realtek driver diffs for unintended changes.
9. Build the kernel/modules using the exact GKID configuration.
10. Test module load, USB enumeration, firmware selection, interface creation, scanning, association, traffic, disconnect/reconnect, and existing adapters.

## Decision

Do not start by copying the upstream subdriver or editing the target core. First complete a line-by-line dependency map for the shared file-operations and core changes. If a complete compatible backport cannot be validated with a real build environment, stop before producing or flashing a kernel ZIP.
